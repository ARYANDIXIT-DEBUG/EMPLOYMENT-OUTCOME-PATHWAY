## 1. Why this file exists

The project's validity depends on one question the audit (`src/data_audit.py`) answers on real files: **can the same person be followed across two or more time points through a verified linking key?** This file records where each candidate dataset comes from, what it can and cannot support, and what must be confirmed before any column name or code goes into `config.yaml`.

## 3. PLFS: what to obtain and check

Do these on the official portal, not from memory or from third-party summaries.

1. **Which release(s)?** Download the person-level file for each release you intend to use. Record the release name and period. **[VERIFY]**
2. **Design.** Note which sampling design each release uses. The 2025 redesign is reported to differ from earlier PLFS designs **[reported, unverified]**. Files from different designs are **never pooled** unless you write a justification into `data.design_mix_justification` (the audit reports each design separately either way). **[VERIFY]**
3. **Data dictionary and layout.** For every file, get the official layout: column positions or header names, code lists, and the questionnaire. Code lists differ between releases **[reported, unverified]**, so one release's codes are never reused for another. **[VERIFY]**
4. **Linking key.** What identifies a person and what identifies a visit or month? The audit checks the key you declare. It does not guess one. **[VERIFY]**
5. **Weights.** Which multiplier applies, and whether it is valid for revisit records. Leave `data.schema.weight` null until confirmed. **[VERIFY]**
6. **Status variable.** Which variable is *current weekly status* for each visit? Usual, subsidiary and current weekly status are different reference periods and are never treated as chronological steps. **[VERIFY]**
7. **Non-response / casualty codes.** Are they recorded per visit? Only where recorded can a record be classified as lost to follow-up. **[VERIFY]**
8. **Training variables.** Which columns record vocational training, and what universe (who is asked)? See open question 1.

## 4. Setting up the files

1. Put the downloaded files under `data/raw/`. Never share or commit them if the terms forbid redistribution. The release ships `data/raw/` empty.
2. In `config.yaml` fill, from the official layout:
   - `data.files`: one entry per file (`id`, `path` under the project root, `release_id`, `design_id`, `period`, `sector`, `kind`, `role`). The example shape is in the file's comments.
   - `data.layouts`: keyed by file `id`; format (`csv` or `fixed_width`), encoding, and for each canonical column where it lives.
   - `data.schema`: the canonical roles (`person_id`, `visit`, `status_col`, `nonresponse_col`, `training_cols`, and so on) mapped to the verified columns. `sex`, `social_group` and `religion` are protected roles: profiling only, never clustering inputs.
   - `states[].raw_codes`: replace each `UNVERIFIED:<name>` placeholder with the codes checked against the questionnaire. `unknown_codes` and `lost_codes` likewise. While any `UNVERIFIED:` code remains, a real run is refused.
3. Run the audit. It prints counts only and builds no model:
   ```
   python run_pipeline.py --stage audit
   ```
   (`python -m src.data_audit` does the same audit; with `data.files` empty it prints "Nothing to audit" and exits 0.)
4. Read the output and resolve the CHECKPOINT 1 findings. Record `data.checkpoint1_status: PASSED` only after official linkage/design definitions and every audit blocker are resolved. Set `data.plan: A` only if the documented design supports the intended trajectories.
5. Obtain the 2023–24 rider and written permission for using `b4q12` to select trainees. Record `data.b4q12_permission_status: CONFIRMED` only with the decision source, approver and date. The dictionary label alone is not permission.
6. Verify and map casualty/nonresponse codes and its column. An empty `lost_codes` or unset `data.schema.nonresponse_col` blocks the real-data run; never add an inferred code.
7. Establish dated training completion before each employment observation with official documentation and person-level evidence. `coarse_flag` is not enough; set timing status to verified only after the timing proof exists.
8. Reconcile the current `data.verified: true` claim with official source documents and write who checked what. Set `baseline.locked: true` once its definition is final.
9. Run `python run_pipeline.py`. Exit code 3 means a safety gate refused; the message names the unmet condition. Never bypass the gate.

## 5. Open questions (each blocks something)

1. **What does `voc_compl` refer to?** The project owner's review says the CY2025 person dictionary (catalogue 284) contains `voc` and `voc_compl`, and that `voc_compl` may refer to a vocational course **or** an entrance/exam course ("col 17 or col 18") **[reported, unverified]**. Until the questionnaire settles this, it cannot define "recently completed vocational training". The audit flags this automatically as `refers_to_ambiguous`. *Blocks:* the `recent_completion` trainee definition.
2. **When did the training happen relative to the observed outcomes?** If unknown, the project may say "ever-trained persons" and may not say "after skilling". That wording is allowed only with `trainee.timing_support: dated` plus evidence. *Blocks:* all post-training wording in the report.
3. **Is `time.n_points: 4` right?** It is a placeholder from the owner's note. *Blocks:* trajectory length, the baseline's `reference_visit`, and stability `censor_points`.
4. **Can about four monthly observations support the word "pathway"?** Only weakly. Four monthly points describe a short window of labour-market states, not a career path. The report template says so. This is a limitation to state, not a reason to stop.
5. **Do the data-use terms permit using `b4q12` for trainee selection, and which profiling variables are allowed?** See `docs/DATA_USE_ASSESSMENT.md`. *Blocks:* real-data selection, modelling and profiling until confirmed.

## 6. What this project will NOT do with these sources

- Combine separate cross-sectional files as if they were trajectories.
- Treat usual, subsidiary and current weekly status as sequential steps.
- Pool records across designs without a written, approved justification.
- Use sex, social group or religion as clustering inputs (profiling only, where permitted).
- Recode missing or unknown records into employment states.
- Name a pathway before real-data cluster profiles exist, or present synthetic output as a result.
